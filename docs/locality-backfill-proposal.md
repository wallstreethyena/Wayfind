# Filling `wf_inventory.locality` — what shipped, and the decision left for the owner

Measured 2026-10-30. **Nothing in this document has been applied.**

## Why locality matters

A place page cannot name its city without it. Measured on the live site:

| measurement | value |
|---|---|
| `/places/[id]` titles carrying **no city** | **81%** (sample of 223 live pages) |
| place pages sharing a **duplicate title** | **115** across 38 titles — "The Home Depot" ×6, "Walgreens" ×6, "Target" ×5 |
| `LocalBusiness` JSON-LD with a real `addressLocality` | near zero — a bare street string, or `"Florida"` (a state in the city field) |

PR #2069 fixes the *code* path (one city ladder: parsed address → `wf_inventory.locality` → guide city, with states rejected). It cannot invent data, so coverage is now the binding constraint.

## Coverage today

| scope | rows | with locality | % |
|---|---|---|---|
| all `wf_inventory` | 21,525 | 3,265 | **15.2%** |
| indexed (`wf_place_ids`) | 17,889 | 3,083 | **17.2%** |

Indexed places still missing a locality: **14,806**.

## Step 1 — shipped here: owned evidence only (122 rows)

`supabase/migrations/20261031000000_wf_inventory_locality_from_owned_events.sql`, generated by `scripts/backfill-locality-from-events.mjs` (read-only; the owner applies).

Source: **`wf_events.city`** — the venue city an editor typed from the organiser's or venue's own page, already linked to the place by `place_id`. Wayfind-owned content. No Google content, no geocoding, no coordinate read or written.

- **122 rows, Tier A only**: unambiguous (exactly one distinct city across that place's events) **and** the event's own `address` text contains that city, so each row corroborates itself.
- 36 further rows are Tier B (unambiguous, uncorroborated) and are **held back** — re-run with `--tiers=AB` to include them.
- 0 excluded as ambiguous.
- Idempotent (`and btrim(coalesce(locality,'')) = ''` on every statement), resumable (that clause is the resume condition), append-only, reversible (`supabase/data-fixes/..._REVERSE.sql` clears only values still exactly as written), auditable (`docs/audits/..._csv`, one row per change with its evidence event and address).

Effect if applied: indexed coverage **17.2% → 17.9%**. Small, and completely safe.

## Step 2 — the owner's decision: the remaining ~14,700

Two routes exist. Both need an explicit decision; neither has been started.

### Option A — derive from the Google Places address already cached

The `pd1|` detail cache holds `formattedAddress` for places whose details have been fetched. `lib/placeCity.js#cityOf` already parses a city out of that shape correctly and is unit-tested against real addresses.

- **Cost:** zero new API calls.
- **Blocker:** writing a *derived, persisted* column from provider content is a licensing question under the Places terms, which is why this repo already keeps Google-derived coordinates in a separate provenance-tracked path rather than in the main columns (see `scripts/migration-pending-apply.json`, the `independent_coords` work, and counsel Q1 on #1809). **This needs the same counsel answer before anyone writes it.**
- **Coverage:** unknown until measured; bounded by how many places have a warm detail cache.

### Option B — bulk reverse-geocode from `lat`/`lng`

Every inventory row has coordinates. Concrete shape if the owner wants it:

| item | proposal |
|---|---|
| **Provider** | US Census Geocoder (`geocoding.geo.census.gov`) — **public domain**, no API key, no attribution requirement, no licensing entanglement. Already the provider this repo used for the `independent_coords` work, so the provenance pattern exists. |
| **Cost** | **$0.** Free, unmetered. Rate-limited by courtesy, not billing. |
| **Volume / time** | ~14,700 rows; batch endpoint takes 10,000 addresses per file, but reverse-geocode is per-point. At 5 req/s ≈ 50 minutes. Resumable, so it can run in chunks. |
| **Provenance** | Written as a new `signals.locality_source = "census-reverse-geocode"` alongside the value, never silently. **Coordinates are read only — never written, never altered.** No Google content is involved at any point, so this does not depend on counsel Q1. |
| **Accuracy** | Census returns the incorporated place / county subdivision for a point. Good for addressed venues; weaker for unincorporated areas and large parks, where it returns the county subdivision rather than a name a visitor would use. |
| **Sample-quality gate before any bulk run** | Reverse-geocode a random **200** rows, diff against the 3,083 rows that already have a locality (hold-out accuracy), and hand-check 25. **Proceed only if hold-out agreement ≥ 95%.** Publish the sample as `docs/audits/locality-reverse-geocode-sample.csv`. |
| **Exclusions** | Any point whose Census answer is empty, is a state/country word, or disagrees with an existing locality is **excluded, not overwritten**. Non-Florida rows (e.g. `metro = dubai-dubai`) are out of scope — the Census geocoder is US-only. |
| **Reversibility** | Same pattern as the migration here: one `update` per row, reversible by exact value match, full audit CSV. |

**Recommendation:** Option B. It is free, public-domain, carries no licensing question, and keeps coordinate provenance untouched. But it is a bulk write to production data on 14,700 rows, so it needs the owner's go-ahead and should not run until the 200-row sample clears the 95% gate.

## What is NOT claimed

No indexing or ranking improvement is promised here. Naming the city makes each page's title and `addressLocality` truthful and distinct; whether search engines or AI tools surface them more is theirs to decide.
