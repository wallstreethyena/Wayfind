## Ryan's root cause

Ryan's is eligible for `food:cafes`: it is OPERATIONAL, not excluded, rated 4.9 from 205 reviews, has primary type `coffee_shop`, and is 3.2 mi from the Parrish center.

`serveFromInventory` (lib/inventoryServe.js) read `wf_inventory` with `limit=1000` over a bounding box and **no `order=`**. The Parrish food box for the café request (radius snapped to 32,000 m) held 1,598 food rows, so PostgREST returned an arbitrary 1,000 in heap order, and the café filter and ranking only saw those rows.

The exact production URL, replayed, came back without Ryan's. The same filters read with `order=place_id.asc` and Range paging included it. Which rows fell out changed whenever the table's heap reshuffled. The edge cache (24 h) then froze different answers in different cache partitions: the same URL returned 134 cafés without Ryan's and 152 with it.

Same-origin proof: the browser runs grant GPS at the Parrish center. The captured `inv=1` request carried the same lat/lng (to 4 decimals), and the expected set is recomputed from the captured request, never from a fixture. No origin mismatch was found.

## Remaining legitimate exclusions
- **Outside the reader's radius**: server gate `radius × 1.15`, and the list's "within" slider (17 mi by default).
- **Brand collapse**: in general feeds, one best branch per chain, using the real `dedupePlaces` rule.
- **Not OPERATIONAL, excluded, or unrated**: `rankInventory`'s own gates.
- **Identity reject**: the place is not that chip under `placeAllowed` / `chipIdentity`. Category law is unchanged.
- **Rank caps**: legitimate only where the next page is proven reachable. The API walk and the browser "Wayfind 5 more spots" walk both run to exhaustion.
